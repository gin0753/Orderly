## Anonymous authentication: external events, not polling

At baseline `22899c4`, visible focus/visibility events restarted `bootstrapCustomer()` after anonymous state had settled. Expected startup is `/me` 401, coordination `/me` 401 inside the Web Lock, then refresh 401 and stable unauthenticated state. The second identity read protects against a peer tab rotating shared cookies; it is not an accidental HTTP retry. An expired access token with a valid refresh cookie follows 401/401/200/200. Terminal refresh failure does not retry indefinitely.

The fix skips automatic focus checks only for settled anonymous state when BroadcastChannel is supported. It preserves initial mount/reload, explicit retry, authenticated validation, peer `changed` bootstrap, peer `ended` expiry and bounded focus fallback without BroadcastChannel. No polling timer or online listener was found. Original probe accumulated 12 requests (startup/focus/visibility/reload), corrected probe 6 (startup/reload); idle windows do not certify indefinite production observation. Severity was P3, no demonstrated session correctness/load defect. Six component suites / 35 tests and the final anonymous+account browser selection 6/6 passed; broad release gate was not rerun for that fix.

See [bootstrap](../../apps/web/src/features/customer-auth/components/customer-auth-bootstrap.tsx), [component cases](../../apps/web/test/customer-auth-bootstrap.test.tsx), [browser cases](../../apps/web/test/browser/customer-anonymous-auth.spec.ts). [Google operations](../operations/google-oauth.md) retains configuration and live-provider requirements.

A controlled pending request reproduced timeout and authenticated `/me` 200: navigation began 6.338ms after logout initiation. This does not prove the two earlier overwritten failures had the same exact cancellation stage. The synchronized helper observes the response before clicking, requires 204, signed-out UI, absent cookies and old-access rejection. Real Google was not exercised.

A forced reload/address-bar replacement while still Signing out remains a lifecycle question; a click alone never guarantees revocation.

Recorded correction: 4 account cases, 27 focused web cases, 23 API unit, 121 integration and uninterrupted 62-case production browser gate passed. ## Image load/decode readiness and viewport isolation

The initial helper bounded required-image work at eight seconds, distinguished missing/load/zero-dimension/decode rejection/decode timeout, and gave optional imagery a two-second diagnostic budget. Offscreen unloaded lazy images are deferred, not claimed decoded. An independent Node watchdog bounds page work when browser timers stall; it does not cancel in-flight evaluate, which test teardown closes. Required photos still fail on every relevant failure, with scroll-to-visit and positive dimensions; optional warnings never apply to hero/configured product/dialog photos. Final isolated helper 30/30 passed, while guarded full database checks were blocked before reset due unsafe target/unavailable Docker. Those helper passes were not a complete storefront pass.

At `98d4790`, resizing the outgoing storefront document immediately before navigation reproducibly left the 390px Wings candidate connected/visible with `complete=false`, zero dimensions, empty selected source and two optimizer requests without completed response. Three uncorrected repetitions: 21 passed / 3 failed at the unchanged eight-second limit. `about:blank` before viewport change ends the outgoing document; three corrected production repetitions 24/24 and three local CI development repetitions 24/24 passed. Optimization remained active. Cold-cache timings alone do not prove an optimizer defect, a decode failure or hosted contention. The exact browser/Next cancellation/coalescing mechanism and original reported Pepperoni CI root cause remain unconfirmed.

The full original selection plus continuation was 60 passed / 1 failed, not a green uninterrupted run; its account logout timeout was separate. Later logout correction obtained a clean complete gate. CI failure artifacts retain sanitized image state/request JSON for seven days, excluding raw trace/cookie/console text. Only validated public menu paths and numeric optimizer width/quality are included. Existing render/contrast/focus/modifier/cart assertions, production optimization, zero retries and deadlines were preserved.

## Hydration, interrupted RSC requests and repeated WebKit loading

11 October baseline `d1d293b` plus accepted cleanup: five retained combined traces had 13 React #418 hydration events (eight `/account`, five history) and 12 native access-control messages for same-origin Next RSC GETs. Development and focused SSR regression proved customer bootstrap could advance the store before a streamed Suspense boundary hydrated. Passing the captured initial state as Redux Provider `serverState` fixes the server/client snapshot race; the regression fails before, passes after and requires eventual authenticated content. It does not change bootstrap/auth APIs or ownership. See [provider](../../apps/web/src/store/store-provider.tsx), [SSR regression](../../apps/web/test/store-provider-hydration.test.tsx), [browser hydration](../../apps/web/test/browser/customer-hydration.spec.ts).

Access-control logging persisted without hydration errors. Main-frame transitions canceled same-origin prefetches; WebKit's adapter promotes native JavaScript/error-level console records to Playwright `pageerror`. Six observed canceled RSC requests and nearby warnings, without unhandled application exceptions, support a navigation/runtime diagnostic artifact for that reproduced group. This is not evidence that every future warning shares that cause, or that authenticated deployed API CORS works. A deployed GET/HEAD/OPTIONS-only comparison blocked mutation requests, observed expected anonymous 401s and rendered public documents; it did not verify deployed authenticated sessions/native Safari.

Three fresh engine selections passed 45 tests, including 36 hydration cases at 1440/390/320px with immediate/500ms session responses. First focused WebKit run had stale synthetic registration 409; fresh guarded fixtures passed unchanged 15/15. Earlier concurrent expanded component/combined journey failed, with CLR startup failure and about 329 MiB free memory; unchanged sequential component retries passed. The sequential combined WebKit run passed four cases plus one existing Chromium-only performance skip, 70 axe scans with no reported violations, zero hydration errors and eight native access-control entries. Historical broad failures are not erased, host pressure is supporting evidence rather than proof of every timeout, and incomplete axe findings are not compliance passes.

Earlier resumed release verification passed 61 Chromium cases and complete four-width Firefox/WebKit journeys while recording the 13/12 errors. Historical repeated-loading timeout was not reproduced; neither `serverState` nor isolated readiness passes establish its original cause or permanent resolution. The final sequential readiness samples were 712/1306/1273/499ms at 1440/768/390/320px. Native Safari/Android, screen reader/keyboard/safe-area, authenticated deployment/performance and operational restore remain separate conditions. See [sanitized lifecycle fixture](../../apps/web/test/browser/release-loading-diagnostics.fixture.ts).
